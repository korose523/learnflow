## 2. 核心算法：瓶颈识别与改进（对应需求 4–6）

被审计算法选定为 **难度公制层** `difficulty_fusion.py`，理由：它是 O8（fused6 + 闭式 λ）与 O11/O12（符号校正 + 可靠性加权 srw7）的**落库实现本体**，所有 difficulty 数字最终都由它产出，属于"论文里每一个难度值都必须能被机器复算"的那段代码。

### 2.1 识别出的瓶颈

| 编号 | 瓶颈 | 位置 | 性质 |
|---|---|---|---|
| B1 | `_rank_average(z_0)` 被重复计算 `m-1` 次（每次一趟 O(n log n) 排序） | `estimate_optimized_difficulty` 的符号校正 | **冗余计算** |
| B2 | 逐题 `sum(w[i]*s[i]*z[i][idx] for i in ...)` / `sum(z[c][idx] for c in COLS)`：O(n·m) 次生成器帧分配 + 跨行二级索引 | 两个估计器的融合段 | **冗余计算 + 数据结构不友好** |
| B3 | 7 路信号全量物化为 `list[list[float]]` 后按 `[i][idx]` 随机跨行访问 | `estimate_o8_difficulty` | **缓存不友好** |
| B4 | `FUSED6_COLUMNS` 判定用 tuple 线性查找 | `estimate_o8_difficulty` | 微瓶颈 |
| B5 | `max(min(q, 1-EPS), EPS)` 同一裁剪值算两次；排序键为 Python 层 lambda | `ecdf_logit` / `_rank_average` | 微瓶颈 |

### 2.2 改进实现

* **B1** → 预先算一次参考列的秩 `r0` 与二阶统计量 `mb/vb`，新增 `_pearson_vs_fixed(a, b, mb, vb)`（算术表达式与 `_pearson` 逐字一致，故返回值位等价）。
* **B2/B3** → 按列缩放为普通列表后 `map(sum, zip(*rows))`：一次 **C 层转置 + C 层求和**，值序列与旧实现逐项相同。
* **B4** → 模块级 `_FUSED6_INDEX_SET = frozenset(FUSED6_COLUMNS)`，O(1) 查表。
* **B5** → 单次三元裁剪 `p = EPS if q < EPS else (1-EPS if q > 1-EPS else q)`；`sorted(range(n), key=values.__getitem__)`。

### 2.3 过程中的两个关键发现（比提速本身更重要）

**发现一：朴素就地累加不等价于内置 `sum()`。**
最初把融合段改成 `fused[idx] = fused[idx] + wi*z[idx]`（更省内存），门禁立刻报 **615/2802 项不相等**，典型 diff ≈ 4.4e-16：

```
o8/rand#0 idx 0: new -0.9132953058511848   old -0.9132953058511849   Δ=1.11e-16
```

根因：**CPython ≥3.12 的内置 `sum()` 对浮点采用 Neumaier 补偿求和**，朴素 `acc = acc + x` 不补偿，因此会在末位 ulp 发散。备选方案实测：

| 融合段实现 | n=3000 耗时 | 与旧实现逐位一致 |
|---|---|---|
| 旧 `sum(generator)` | 1.400 ms | —（基准） |
| 朴素就地累加 | 0.446 ms | ❌ 否（615 处不等） |
| 手写 Neumaier | 1.53–1.68 ms | ✅ 是，但**比旧实现更慢** |
| **`map(sum, zip(*rows))`** | **0.785 ms** | ✅ **是，且最快** |

结论：**用内存换正确性 + 换速度**——保留行缓冲（额外内存 ≈ 7n 个指针，n=3000 时约 170 KB，float 对象本身复用），换来 bit-exact 且 1.35×–1.49× 提速。这条权衡已写进模块 docstring 的"刻意未做的改动"清单。

**发现二：一处真实的数值陷阱（不是重构引入，而是重构暴露）。**
`FUSED6_COLUMNS = (0,1,2,3,5,6)` **包含索引 0**，所以 fused6 累加的必须是 **success_rate 取负之后**的那一列。旧实现靠 `transformed[0]` 隐式保证；重构时若让 `success` 与累加列持有不同对象，就会退回未取负的原值。已由位等价门禁捕获并在代码注释中固化说明。

## 8. 本轮新增：M4 算法效率优化（秩矩阵外提，2026-09-27 续，对接"优化算法性能与效率"需求）

### 8.1 瓶颈与修复

**瓶颈（纯 Python 下的真实开销）**：M4-B 求解 β=V⁻¹q 需秩相关矩阵 V，其每一项是两列**平均秩**的 Pearson。在部分可观测（M4-D，coverage 非空）的**逐题（per-item）β** 路径下，`m4_beta` 原本每次调用都在内部对全部 m 列重排一遍；但标准化列 `zstd` 的秩对**所有题目相同**（item-invariant），于是 n 道题被重复排序了 n 次——构成 O(n) 的冗余因子，是逐题路径在纯 Python（无 numpy）下的主导成本。

**修复（秩外提）**：
- `difficulty_m4.py`：新增 `_rank_covariance(rk)` 与 `_m4_beta_from_ranks(zstd, rk, q)`；`m4_beta` 改为委托前者（公开 API 行为不变）；`incremental_columns` 新增可选 `ranks_` 参数复用调用方秩；`estimate_m4_difficulty` 在逐题循环外算一次 `rk_zstd` 并透传，循环内不再排序。
- `run_m4.py`（实验主程序，产出 `m4_results.json`）：`beta_from_q` 同样增加可选 `R` 参数；`all_variants` 在 `:171` 算一次 `R=[rank_average(c) for c in Zstd]` 后透传，删除原 `:202` 处重复的 `Rk` 赋值。

### 8.2 行为保全证明（最关键）

优化**不改变任何数值**：`rk` 由同一 `ranks`/`rank_average` 函数算得、V 与高斯消元 `_solve`/`solve` 完全不变。两条独立证据：
1. **单元层**：`tests/test_difficulty_m4.py` 新增 `TestEfficiencyRefactor`（4 条）——`m4_beta` 与秩外提版逐位相同、`ranks_` 透传不改变增量列、逐题路径可复现、与内联重算（优化前行为）逐位相同。离线复跑 **44 PASS / 0 FAIL / 0 ERROR / 0 SKIP**（原 33 + 残差化 7 + 效率保全 4）。
2. **实验层**：`m4_results.json` 完整复跑（dbe_r=20 / jun_r=8 / holdout 8×10）后，与优化前备份 `diff -q` **逐位相同（byte-identical）**——论文全部数值（DBE k=200 m4_full 0.0796 / m4_E_cf 0.1718；Junyi m4_full 0.2709；holdout m4_full 0.7289 / m4_E_cf 0.9498 等）保持不变。

### 8.3 实测加速比（`python results/code/benchmark_m4_efficiency.py`，m=7 列、部分可观测合成数据）

| n | 优化前 (ms) | 优化后 (ms) | 加速比 |
|---|---:|---:|---:|
| 100 | 54.50 | 42.51 | 1.28× |
| 200 | 216.65 | 161.45 | 1.34× |
| 400 | 905.70 | 652.98 | 1.39× |
| 800 | 3772.13 | 2584.87 | 1.46× |

加速比随 n 单调上升（冗余的 O(n) 排序因子在较大 n 下占比更大），验证瓶颈定位正确；DBE 实规模（n≈212）约 1.34×。收益来自消除重复工作，零精度代价。

### 8.4 诚实缺口（未做 LU 分解加速）

V 在逐题路径中对所有题目相同，理论上可一次 LU 分解 + n 次前向/回代（O(m³)+O(n·m²)）进一步把 O(n·m³) 降为常数。本文**未采用**：① 项目浮点红线要求每个数字机器可复算、逐题求和走 Neumaier 补偿 `sum()`；② LU 分解会改变高斯消元内部浮点求和次序，虽数学等价却可能在末位 ulp 发散。因本优化已在不触动 `_solve` 的前提下消除冗余且保真，故选"零精度代价"而非"更激进提速"；LU 分解留作纯冷启动生产路径（不经外生复算）的未来优化。
