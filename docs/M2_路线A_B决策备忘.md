## 0 审阅原文（决定依据）

> **6.1 致命 — 作为内部静态审计有效，但结论大于材料。** 77.8% 不可归类的原因，稿件自己写了："`target_construct`, `channel`, `side_effect`, `precedence` 四个字段在代码中根本不存在"。这是学生设计的七元组、学生写的代码没有实现的事实。把事前固化的 schema 套到真实代码上找出不可达路径与实现空白，作为有限的内部静态审计是有效的。但它更像是实现未完成的诊断，而非证伪条件触发的"发现"，从这一诊断推不出关于系统一般的结论。运行时冲突 1 对·预算竞争 0 的原因也是"28 个次级机制只写评估记录、不构造干预效果""干预效果生产者只有 2 处"。真实用户日志为 0。材料无法区分"冲突稀少"与"没有能发生冲突的运行时"。跨系统复现是 Moodle/PHP 插件 2 种、单一编码者、无评分者间信度。在此基础上得出"多数同类系统通过结构设计规避冲突"的一般结论，n=2。《软件学报》评审人会问"其他系统设计者从这次审计学到了什么"。现在的答案是"只登记机制而不产生效果就没有冲突"，这不是发现。

> **6.2 两条路线选一条**（路线 A 实证强化 / 路线 B 缩减，详见下）。
> **6.3 重要**：参考文献 17/20 不在 bib；审计时点快照不可复现"对审计型论文而言是致命的，给审计时点的树打 tag"；成熟度文档 9/41/4 与实测 9/37/8 的漂移稿件写了，而报告用的是 4。

> **§0 裁决**：M2 = 暂缓投稿 → **重构**。作为内部静态审计与未实现诊断是有效的，但缺少运行时频率与外部泛化的实证。从 6.2 节两条路线中选一条重做。

## 2 路线 A：实证强化

### 2.1 三项工程增量（缺一不可）

| # | 增量 | 具体验收标准 | 影响的稿件章节 |
|---|---|---|---|
| A1 | **账本从设计规格变为实现** | 落地 `budget_consumed`、`preempted_by` 与 `ArbitrationTrace` 落库（第 5 章 schema 原样实现）；§5.2 三类一致性检查**首次产出数字** | §5.1、§5.2、§10 |
| A2 | **效果生产者由 2 提升到 ≥ 14**（28 个次级机制中至少一半） | 全仓库 `Effect(` 构造点由 2 增至 ≥ 14，且分布于同一决策点；改造前后**并列报告** | §3.3.2、§3.3.3、§3.4 |
| A3 | **合成会话通过编排器** | ≥ 10,000 会话 × 40 步（学习者模型复用 M3 模拟器），产出**运行时冲突频率 / 预算耗竭率 / 抢占违规率**三个分布 | §3.3、新结果节 |
| A4 | **外部系统扩样与双编码** | 外部系统 ≥ 4 个（Moodle/PHP 生态之外 ≥ 1 个）；两名独立编码者；报告 **Cohen κ** | §6 |

### 2.2 收益

- 第 3.3～3.4 节三条结论（27→1、0、死代码）**从静态推断升级为实测**；
- 审阅 §6.1 的三条批评**逐条被消解**：结论不再大于材料（有运行时分布）、"冲突稀少 vs 不可发生"有了判别手段（A2 使运行时**可能**发生冲突，故 0 才有信息量）、n = 2 无信度被 A4 处理；
- 审阅 §6.2 的"其他设计者能学到什么"获得实质答案：**不是**"不产生效果就没有冲突"，而是**冲突频率—生产者数量—预算强度**三者之间的实测关系。

### 2.3 代价与风险

1. **改造被测系统本身**。A2 会改变审计对象：它不再是"自然状态下的系统"，而是"为通过审计而改造过的系统"。**缓解**：改造前后并列报告（登记规模 54 / 生效规模 2 → N），并把 A2 后的冲突频率**只**解释为"生产者数量对冲突频率的敏感性"，不解释为对原系统的修正。
2. **A3 的合成会话只能给出"机制性"结论，不是教学性结论**。奖励口径仍是即时成功率类代理，不能宣称学习增益。
3. **工作量最大**：A1 + A2 + A3 + A4 是一个完整的工程周期，且 A2 触及仲裁器与编排器的核心路径，回归测试须同步扩充（当前全量 972 条）。
4. **审阅 §2.3 的计划级问题仍在**（自有数据为 0、RQ2 未执行），路线 A 不能替代计划书 v1.1 的修补。

### 2.4 适用条件

若目标是**发一篇实证软件工程期刊论文**（JSS / EMSE / IST），且能在计划书 v1.1 定稿后投入一个完整工程周期，则选 A。

## 3 路线 B：缩减

### 3.1 拆解方案

| 产物 | 内容 | 体裁定位 |
|---|---|---|
| **学位论文第 4 章（治理链）** | 干预七元组的形式化、三类冲突判据、账本 schema、Merkle 锚定论证、合规抢占性质 S1——全部作为**设计规格**呈现 | 学位论文章节，允许"设计 + 实现现状"混合 |
| **短经验报告**（研讨会 / 短文，8–10 页） | 核心 = **"仲裁层的存在不等于仲裁路径的可达"** + 一次自审的三个数字（77.8% 的实现诊断、27→1、0）+ 一条设计需求（先清点 `Effect` 构造点再谈仲裁） | 经验报告 / experience report |

### 3.2 收益

- **不额外投入工程**，现有材料在"内部审计 + 负结果 + 自我批评"这一体裁下是**成立的**；
- 短经验报告恰好容纳"我们按自己的 schema 审计了自己的系统，发现四个字段没实现、一层仲裁从未被走到"这一**体裁**——这正是审阅所说"其他设计者能学到什么"的诚实答案；
- **封存自然状态**：改造前的自然状态数据只有现在这一次机会；先定稿等于先封存，对未来路线 A 的对照有独立价值；
- 与审阅 §7 的建议顺序一致（"先固定计划书 v1.1，再把 M1 打磨为第一篇投稿，M2·M3 在其后"）。

### 3.3 代价与风险

1. **放弃期刊论文**——M2 不再计入期刊产出，毕业口径须由 M1（与计划书 v1.1）承担；
2. 审阅 §6.1 的批评在路线 B 下**部分保留**（仍无运行时频率），须靠**体裁适配**而非**新数据**来化解：把"频次结论"整段降级为"内部审计的性质描述"，只保留可独立举证的那一条命题；
3. 短经验报告仍需处理 §6.3 的三项（bib 补齐、审计 tag、成熟度 8/4 一致性）——本次修订已完成 tag 与成熟度部分。

### 3.4 适用条件

若近期的工作重心是计划书 v1.1 + M1（首篇投稿），且 M2 的价值主要在于**学位论文章节**而非期刊论文，则选 B。

## 4 决定与建议（2026-09-22 更新：路线 A 已选定）

> **学生决定（2026-09-22）**：M2 走**路线 A（实证强化）先行**，不再以路线 B 形态先行定稿。理由：实证强化直接消解审阅 §6.1 的三条批评，且 A1（账本）已于决定当日实现，工程可立即推进。

**原建议（供追溯，已被决定覆盖）**：分阶段走路线 A，但以路线 B 的形态先行定稿。具体：

1. **立即**：按路线 B 把 M2 现稿定稿为**短经验报告**（保留第 3.4 节的死代码发现作为核心贡献），完成 §6.3 的三项收尾（tag 已完成、bib 补齐、成熟度口径统一）；
2. **并行启动**路线 A 的 A1（账本实现）与 A2（效果生产者 ≥ 14）——这两项是纯工程，不依赖外部数据；
3. **待 A1+A2 完成并产出合成会话分布**，再补 A4（≥ 4 系统 + 双编码者 INR/κ），然后**以新一轮数据重写**为期刊论文，此时 A2 后的"改造后系统"与路线 B 封存的"改造前系统"构成天然对照。

**决定后的实际推进（2026-09-22）**：A1 账本落地已实现（`app/services/arbitration_ledger.py` + `ArbitrationTrace` 账本字段 + `verify_m2_ledger.py` 门禁）；A2/A3/A4 按路线 A 继续。路线 B 形态（短经验报告 / 学位论文第 4 章）降级为 A2/A3 完成前的里程碑产出。

**理由（两条）**：

- 本文当前**最强的材料**（"仲裁层的存在不等于仲裁路径的可达"）**恰好是路线 B 的体裁优势**；把它压在未完成的路线 A 里等待，收益为负。
- 路线 A 的 A2 会改变被测系统，因此**改造前的自然状态只有现在这一次机会**；路线 B 的先行定稿同时起到**封存自然状态**的作用，使未来路线 A 的对照成立。

**不建议的做法**：以现有形态直接投稿。审阅已明确该形态推不出关于系统一般性的结论，投入审稿周期只会消耗时间。
